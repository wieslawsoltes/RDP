# Security model and deployment limits

## Experimental credential-handling code

Do not treat this release as production-audited software. Use isolated test accounts and non-sensitive lab hosts until independent protocol/security review and server interoperability qualification are complete. The Node bridge handles passwords, authentication session keys and decrypted RDP traffic. Anyone controlling that process, its machine, its origin or injected same-origin JavaScript can compromise those sessions.

The browser-to-bridge connection uses HTTPS/WSS except for the default local development loopback. The bridge-to-server connection uses its own verified TLS channel. CredSSP is terminated at the bridge. These are two separate protected connections, not browser-to-server end-to-end encryption. Do not expose the default bridge as a public SaaS or a multi-user gateway.

## Authentication and certificates

The bridge accepts only target IDs from an administrator-authored allowlist and requires a separate high-entropy access token. A random token is generated by default. `LRDP_TOKEN` can supply an external secret; store it securely and rotate it by restarting the service. Do not put the token in a URL, published profile, screenshot, source archive, browser persistent storage or shared log.

Target TLS authentication normally uses the Node trust store or an explicit CA bundle plus server-name validation. Exact certificate SHA-256 pinning is an administrator-controlled alternative: possession of that certificate's private key is the selected identity, so CA/name authentication is replaced by the configured pin. Validity dates remain checked. Pins must be established through an independent trusted channel, not copied unquestioningly from a failing connection. Pinned renewal is an explicit deployment operation.

TLS-only mode must be enabled on a particular target and chosen by the user. NLA failures do not trigger silent TLS-only fallback. Plain RDP Security, RC4-encrypted legacy RDP sessions and NTLMv1 are not accepted.

MD4 exists for NTLMv2 compatibility; RC4 is used only by NTLMv2 and the specified RDP licensing exchange, both inside independently verified TLS. These protocol-mandated legacy algorithms do not weaken the TLS requirement. They are not offered as general modern cryptographic primitives. CredSSP 5/6 processing verifies the server's nonce-bound public-key hash before delegating password credentials. Negative tests verify that a wrong server binding prevents delegation. The authentication tests use a co-developed peer and cannot replace review of Windows interoperability or cryptographic implementation details.

## Browser origin and endpoint policy

The service requires exact HTTP Host and WebSocket Origin matching, rejects non-loopback HTTP binding, constrains the public origin, uses a self-only Content Security Policy, disallows framing, and serves only selected static source trees. Target inventory requires bearer authentication. Arbitrary hostnames from browser messages are not used as socket destinations. The administrator remains responsible for the allowlist's destinations and DNS integrity.

Connection rates, live sessions, JSON fields, UTF-8/WebSocket frames, stream buffers, bitmap dimensions and channel sizes have explicit budgets. WebSocket masking, control frames and continuation states are validated. These are defensive controls, not evidence that all denial-of-service paths have been eliminated. Authenticated clients can still consume significant CPU/GPU/network resources within their session budgets. There is no per-human identity, durable audit ledger, role-based policy or distributed rate limiter.

## Data lifecycle

Profiles persist only approved metadata. Passwords and bridge tokens are excluded from profile JSON and `.rdp` exports. Clipboard access is explicit; remote clipboard text is shown as text rather than inserted as HTML. Screenshot and clipboard exports can contain sensitive remote data and are deliberate user actions.

Some binary buffers are cleared on disposal and credential references are discarded after use. JavaScript strings, garbage collection and runtime copies cannot guarantee complete secret zeroization. Do not describe this as a secure enclave or zero-retention system. Session diagnostic exports omit passwords and clipboard payloads but can expose certificate/host/network metadata; review them before sharing.

## Not included

There is no OS keychain/vault integration, user account system, Kerberos delegation policy, smart-card logon, Remote Credential Guard, Restricted Admin implementation, recording policy, malware scanning, clipboard DLP, intrusion detection, security certification or automatic update channel. Device redirection is intentionally absent rather than partially exposed without ownership and consent policy.

Before production use, require an independent audit of the custom WebSocket, ASN.1, NTLMv2, CredSSP and binary protocol parsers; long-running stateful/coverage-guided fuzzing; Windows interoperability captures under a controlled consented lab; resource-exhaustion testing; GPU driver/browser matrix testing; dependency/runtime patch policy; and deployment-specific credential/access controls.

## Licensing and stored CALs

The gateway owns licensing keys and receives their public parameters only from
its certificate-verified RDP connection. The browser cannot supply a licensing
key, complete an exchange by control message, or send licensing PDUs through the
protected gateway path. CALs remain opaque server-issued data. Integrity and
cache failures terminate the exchange; activation waits for successful storage.
The legacy licensing MAC/RC4 is protocol compatibility inside verified TLS,
not a replacement for TLS or a modern general-purpose cryptosystem.

The CLI's persistent store uses AES-256-GCM with a stable installation identity,
exclusive process ownership and atomic writes. Protect the key and cache together;
access to both defeats at-rest encryption. POSIX mode/ownership checks are
implemented; Windows deployments need an appropriately private account ACL.
There is no hardware/keychain-bound key protection. No local license is minted
and no server rejection is converted to an entitlement. See the resource,
interop and backup boundaries in [licensing integration](changes/0011-licensing-integration.md).
